# Source-to-screen method and evidence boundary

The baseline already assessed the future capital exchanged in a package, but did not present the active franchise's remaining exact-pick inventory. This extension reuses its canonical ownership and Trade assets; it does not replace that assessment or assign pick/class values.

## Pipeline

1. Read the admitted league's existing native Sleeper traded-pick state, canonical pick ledger and franchise-owned pick views. No source acquisition occurs.
2. Reconcile unique `(season, round, original franchise)` identities, current owners, native transfers and each team's view. Use the league's explicit configured round count and only seasons actually in the ledger. A complete Cartesian domain is proved by valid key domains, uniqueness and cardinality; absent picks are never minted to fill it.
3. Capture the active franchise's before inventory and exact sent/received Trade assets. Existing authoritative validation remains responsible for the offer. A deterministic ownership digest is separate from projection and Market compatibility.
4. Freeze the bounded snapshot with the assessment. The existing temporary workspace/account/league/franchise binding, context limits and selected-offer limits remain in force. Old offers without snapshots do not consult current inventory.
5. Render a small season/round before→after summary, own versus other-franchise firsts, and native expandable identity lists. The two-offer comparison uses the same producer output; keeping the roster uses a shared baseline only when the recorded ownership generations agree. No HTTP work occurs on expand or compare.

## Independent qualifications

Ownership can be supported when projections or recommendation evidence are missing. That does not qualify the trade. Lineup and Neutral/Custom comparisons continue to apply their existing independent provenance and compatibility rules. Counterparty evidence remains attached to its original offer.

Incomplete/legacy inventory withholds remaining totals but preserves otherwise verified proposed movements. Conflicting ownership, duplicates and ambiguous identities are withheld. An oversized recorded inventory retains bounded exact movements and explains unknown totals. A verified empty inventory supports zero; missing data does not.

## Numerical controls

In a disposable 2029/two-round cohort, the active franchise owns firsts from original franchises 1 and 3. Sending its own first (1) and acquiring franchise 2's first changes total firsts 2→2, own firsts 1→0 and other firsts 1→2; franchise 3's exact first remains. Player-only exchanges leave the inventory unchanged. No price or projected future player value is implied.

The authenticated browser controls instead use retained 2028/four-round identities. Offer 1 sends the acquired `2028-R1-3` alongside a player; Offer 2 is player-only. Both are independently evaluated by the existing canonical engine in one-QB/K/DEF and Superflex fixtures. Two alternatives plus keeping the roster survive four viewports, reload and subsequent unrelated ownership changes. A league switch clears their scope. Disposable fixtures, not production user data, supply these controls.

## Resources and preservation

The new family is bounded to a 10k-character record in up to eight chunks and uses the unchanged 64k context/100k offer/200k selected-offer limits. It does not expand the existing 12k/512-node analytical disclosure. Truncated or absent records render unknown, not reconstructed inventory. There is no new database, background worker, provider call, valuation, lineup calculation or synchronization from the panel.

The final 21-case focused container recorded an 822,853,632-byte kernel peak (about 785 MiB), no OOM events, and exit 0. That is whole-fixture/container usage including browser and driver, not incremental feature cost or a before/after production-memory claim. Full mandatory and hosted outcomes must be read from their completed exact-source evidence; interim progress is not success.
